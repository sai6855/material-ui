Autocomplete has props. Why turn them into component types?

The costly path is props → component types → props, inside a generic type comparison. This is compile-time work, not rendering work.

1. Chip and ChipComponent are not the same thing

Chip is the MUI component. ChipComponent is its root component type, which defaults to 'div'.

import * as React from 'react';
import type { ChipProps } from '@mui/material/Chip';

type ChipComponent = 'div';
type DivProps = React.ComponentPropsWithRef<ChipComponent>;
type MuiChipProps = ChipProps<ChipComponent>;

const divProps: DivProps = { id: 'fruit' };
const chipProps: MuiChipProps = { id: 'fruit', size: 'small' };

// @ts-expect-error A div does not have MUI Chip's size prop.
const wrongDivProps: DivProps = { size: 'small' };

ChipProps<'div'> includes Chip-specific props and root div props. Props of 'div' alone do not include Chip-specific props.

2. What comparison starts the work?

import Autocomplete, {
  type AutocompleteProps,
} from '@mui/material/Autocomplete';

function MyAutocomplete<Value>(
  props: AutocompleteProps<Value, false, false, false>,
) {
  return <Autocomplete {...props} />;
}

At <Autocomplete {...props} />, TypeScript checks whether the wrapper's props can be passed to Autocomplete. Value is still generic.

3. Follow the chip slot's existing type path

The library passes this expression into SlotProps:

React.ElementType<Partial<ChipProps<ChipComponent>>>

Inside the slot helper, React.ComponentPropsWithRef extracts props from that component-type union. Here is the middle of that path, exposed as small aliases:

import * as React from 'react';
import type { ChipProps } from '@mui/material/Chip';

// Start with an existing props type.
type KnownProps = Partial<ChipProps<'div'>>;

// Find compatible HTML/SVG tags and custom component types.
type Candidates = React.ElementType<KnownProps>;

// Extract props from those component types again.
type ExtractedProps = React.ComponentPropsWithRef<Candidates>;
KnownPropsWe already have the Chip props.
→

→
ComponentPropsWithRefRecover props from that union.

The slot helper then makes the extracted props optional and adds its slot-specific types.

When generic props types are compared, TypeScript can expand and relate these large nested unions. The round trip is a costly part of that work—not a second validation of the same user object.

The extracted union is not guaranteed to equal the starting props type. It can include intrinsic-element and class-ref branches. These arrows describe type relationships, not eager execution on every keystroke.

4. Why your ChipComponent-only attempt loses information

import type { ChipProps } from '@mui/material/Chip';
import type { SlotProps } from '@mui/material/utils';
import * as React from 'react';

type CurrentChipSlot = SlotProps<
  React.ElementType<Partial<ChipProps<'div'>>>, {}, {}
>;
const current: CurrentChipSlot = { size: 'small' };

type RootOnlySlot = SlotProps<'div', {}, {}>;

// @ts-expect-error This describes div props, not Chip props.
const rootOnly: RootOnlySlot = { size: 'small' };

Passing ChipComponent directly replaces the Chip-compatible component union with its root type. With the default root, the helper extracts div props and loses size.

The empty override and owner-state types above keep this example focused. The actual declaration supplies Autocomplete's owner state. That callback parameter does not restore missing Chip props.
