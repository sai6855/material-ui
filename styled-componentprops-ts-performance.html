TypeScript performance investigation

The real cost of ComponentProps<typeof Styled>

Extracting the props is not the expensive part. The large type-checking jump happens when those extracted props are spread back into the same MUI styled component.

Exact trigger

React.ComponentProps resolves the styled component’s props, then <Styled {...props} /> makes TypeScript structurally compare that resolved object against the styled component’s callable props again.

Two minimal, complete examples

Both files compile. The only meaningful difference is whether the extracted props are applied back to Styled.

Extraction only

TypeScript resolves the props, but does not compare them back to the component.

import * as React from 'react';
import { styled } from '@mui/system';

const Styled = styled('div')({});

type StyledProps = React.ComponentProps<
  typeof Styled
>;

export function Wrapper(
  _props: StyledProps,
) {
  return null;
}
Round trip

The JSX spread forces another structural compatibility check.

import * as React from 'react';
import { styled } from '@mui/system';

const Styled = styled('div')({});

type StyledProps = React.ComponentProps<
  typeof Styled
>;

export function Wrapper(
  props: StyledProps,
) {
  return <Styled {...props} />;
}

What TypeScript has to do

Think of this as a round trip. Extraction creates the props type; the spread sends it back through the component’s overloaded JSX call signature.

typeof Styled An Emotion styled component plus MUI’s common props.
→
ComponentProps Infers one resolved props object. This step is relatively cheap.
→
<Styled {...props} /> Checks the resolved object against styled overloads and their full prop shapes.

Measured compiler work

These are TypeScript instantiation counts from the current repository’s built declaration files using TypeScript 6.0.2. Instantiations are a repeatable measure of generic type work; they are more useful here than noisy wall-clock timings.

ComponentProps only Extract and name the props 1,230
Spread back into MUI Styled Extract, resolve JSX overloads, and structurally compare props 7,568

The key delta is +6,338 instantiations between extraction alone and spreading the extracted props back into the MUI component.

Where MUI’s additional work comes from

MUI adds three common props to the styled-engine component. Isolating them shows that as and sx account for nearly the entire difference. 

interface MUIStyledCommonProps<Theme> {
  theme?: Theme;
  as?: React.ElementType;
  sx?: SxProps<Theme>;
}
Common props included Instantiations
None 3,559
theme 3,559
as 4,909
theme + as + sx 7,531

The expensive branch inside sx

Under the current compiler, the dominant branch is the mapped CSS-property catalog—not the recursive nested-selector branch. 

type SystemCssProperties<Theme> = {
  [K in keyof AllSystemCSSProperties]:
    | ResponsiveStyleValue<
        AllSystemCSSProperties[K]
      >
    | ((theme: Theme) =>
        ResponsiveStyleValue<
          AllSystemCSSProperties[K]
        >)
    | null;
};
  • The mapped type contains hundreds of CSS and MUI system-property keys.
  • During the JSX spread comparison, TypeScript walks those property relationships.
  • Adding sx increased this benchmark by approximately 2,622 instantiations.
  • Adding polymorphic as increased it by approximately 1,350 instantiations.

The precise problem

Spreading props extracted from an MUI styled component forces TypeScript to structurally compare the component’s polymorphic as type and large mapped sx type against its styled overloads again.

The problem is not merely using React.ComponentProps, and it is not the Theme type catalog in this reproduction.

Scope: this page identifies and isolates the current performance trigger. It intentionally does not propose a type design or implementation change.
