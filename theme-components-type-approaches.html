MUI · TypeScript performance

Three ways to type theme.components

Each approach catches component configuration mistakes differently. The examples below use the same deliberate typo—variant: 'contains'—so the trade-off is easy to see.

The useful check

For MuiButton, TypeScript should accept 'contained' and reject 'contains'.

The performance problem

Today, asking for the Button type can instantiate the type machinery for the complete Components<Theme> catalog.

Approach 1 · Current strict behavior

Automatically type every component

No extra declaration file is needed. createTheme expects its components property to match the full Components<Theme> type.

theme.ts

import { createTheme } from '@mui/material/styles';

export const theme = createTheme({
  components: {
    MuiButton: {
      defaultProps: {
        variant: 'contains',
        // ^ TypeScript error
      },
    },
  },
});

Conceptual expected type

components?: Components<Theme>;

// The catalog contains:
// MuiButton
// MuiCard
// MuiDialog
// ...every other Mui* component
Prepare the full catalog→Find MuiButton→Reject 'contains'
Result: excellent automatic type safety, but potentially expensive type instantiation even when the theme customizes only one component.
Approach 2 · Current PR proposal

Enable optimization globally, then restore selected types globally

The feature flag makes theme.components loose. The same module augmentation then restores strict checking for MuiButton across the entire TypeScript program.

mui-types.d.ts

import type {
  Components,
  Theme,
} from '@mui/material/styles';

declare module '@mui/material/styles' {
  interface TypeFeatures {
    optimizedTheme: true;
  }

  interface ThemeComponents
    extends Pick<
      Components<Theme>,
      'MuiButton'
    > {}
}

theme.ts

import { createTheme } from '@mui/material/styles';

export const theme = createTheme({
  components: {
    MuiButton: {
      defaultProps: {
        variant: 'contains',
        // ^ TypeScript error
      },
    },
  },
});
Use the loose catalog→Globally add MuiButton's type→Reject 'contains'
Result: only selected component types are intended to be instantiated. The selection applies to every theme in the program because module augmentation is global.
Approach 3 · Jan's suggestion

Enable optimization globally, but validate each theme locally

Only the performance flag is augmented globally. The satisfies expression beside the theme asks TypeScript to validate exactly the components customized there.

mui-types.d.ts

import type {} from '@mui/material/styles';

declare module '@mui/material/styles' {
  interface TypeFeatures {
    optimizedTheme: true;
  }
}

theme.ts

import {
  createTheme,
  type Components,
  type Theme,
} from '@mui/material/styles';

export const theme = createTheme({
  components: {
    MuiButton: {
      defaultProps: {
        variant: 'contains',
        // ^ TypeScript error
      },
    },
  } satisfies Pick<
    Components<Theme>,
    'MuiButton'
  >,
});
Use the loose catalog→Locally request MuiButton→Reject 'contains'
Result: the selected component list stays next to this theme, and the object keeps its precise inferred type. The PR still needs measurements proving that this form avoids the full instantiation cost.
Comparison

What changes between the approaches?

Approach Component selection Type safety Expected cost
1. Current strict Automatic: all components All component configurations Highest; full catalog may be instantiated
2. PR augmentation Explicit and global Only selected components Low in the PR's measurements
3. Jan's satisfies Explicit and local to each theme Only selected components Not yet established; benchmark requested
Status: the optimization API is proposed in an open PR. Approaches 2 and 3 require those proposed types and are not examples for the currently released package.
